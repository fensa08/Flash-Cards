Consistent Hashing

SECTION 01 · THE PROBLEM WITH MODULO HASHING

When you distribute keys across n servers with hash(key) % n, adding or removing a single server reshuffles almost every key's assigned node. For a cache cluster, that means a near-total cache miss storm every time you scale.

Consistent hashing solves this by mapping both servers and keys onto a fixed ring of hash values. A key belongs to the first server it meets walking clockwise. Removing a server only reassigns the keys that were pointing to it — everything else stays put.

Kiln mentor noteTry this: if you're prepping for an interview, be ready to explain why the miss storm happens with modulo hashing before you introduce the ring — interviewers often probe this first.

In practice, the ring alone isn't enough — a small number of physical nodes maps unevenly onto the ring, so real systems assign each server several virtual nodes to smooth out the distribution. More on that in the next section.

Two approaches dominate current production systems. HNSW graphs remain the default for low-latency, high-recall search on in-memory indexes1, while IVF-PQ variants are preferred once the index outgrows memory, trading some recall for a much smaller footprint2.

A newer thread worth tracking: hybrid indexes that route queries between a graph index and a compressed disk-based index depending on the freshness of the vector3, which is closer to how Kiln indexes your own notes for the mentor's recall.
